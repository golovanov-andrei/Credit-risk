# Демонстрация проекта на собеседовании

## Рассказ на минуту

«Это учебный ML-проект на табличных данных. Я исследую подготовку признаков, дисбаланс классов и путь от эксперимента до работающего приложения. В исходном CSV нет наблюдаемых дефолтов: метка создана простым правилом. Поэтому я не представляю результат как модель реального кредитного риска.

В поддерживаемой версии единый Pipeline используется при обучении и предсказании. Преобразования обучаются на train, порог выбирается на validation, затем формируется отчёт на test. Есть CLI, Streamlit, SQL-анализ и тесты, проверяющие критичные границы.

Accuracy у модели и majority baseline совпала: 98.5%. При этом baseline не нашёл положительных записей, а модель нашла 2 из 3. Это показывает, почему для редкого класса я рассматриваю precision, recall, F1 и PR-метрику. Следующий исследовательский этап требует данных с настоящим наблюдаемым исходом».

Перед использованием этого рассказа разберитесь в коде и сформулируйте собственные решения своими словами. Изменения, подготовленные с помощником, не следует выдавать за полностью самостоятельную работу.

## Показ за 3–5 минут

1. README: задача, границы, таблица результатов.
2. reports/metrics.json: размеры выборок, порог, confusion matrix и baseline.
3. src/credit_risk/data.py: контракт, обработка пропусков, границы искусственного правила.
4. src/credit_risk/model.py: разбиение, Pipeline и выбор порога.
5. CLI-предсказание, затем Streamlit с теми же входными данными.
6. Один тест согласованности предсказаний и один тест восстановления log-odds.
7. Ноутбук: SQL с CTE и оконной функцией.

Команды из активированного окружения:

```bash
python -m pytest
python -m credit_risk.cli train
python -m credit_risk.cli predict --input examples/applicant.json
python -m streamlit run app.py --server.address 127.0.0.1
```

В форме выберите сумму 9000, срок 36, текущий счёт little. Затем поменяйте срок на 24: точное правило сменит метку. Модель может аппроксимировать границу иначе — это предмет обсуждения, а не ошибка демонстрации.

## Вопросы, к которым стоит подготовиться

| Вопрос | Что объяснить |
| --- | --- |
| Зачем ML, если правило известно? | Для исполнения правила он не нужен; это демонстрация инженерного цикла и анализа ограничений |
| Почему не accuracy? | При 3 положительных примерах из 200 постоянный нулевой ответ уже даёт 98.5% |
| Чем PR-метрика отличается от ROC-AUC? | Она показывает поведение ранжирования относительно редкого положительного класса; интерпретировать вместе с prevalence |
| Где выбирается порог? | Только на validation; тестовые метки не передаются select_threshold |
| Почему Pipeline? | Для сохранения обученных преобразований и одинакового пути обучения/инференса |
| Что означает пропуск счёта? | Неизвестное значение; отсутствие счёта не установлено |
| Почему Job категориальный? | Код занятости не превращается в предположение о линейных расстояниях между профессиями |
| Почему исключён Sex? | Он не нужен для этой демонстрации; его исключение само по себе не доказывает справедливость |
| Как работают объяснения? | Через коэффициенты в пространстве после preprocessing; сумма вкладов восстанавливает log-odds |
| Что мешает реальному применению? | Искусственная цель, происхождение данных, малая выборка, отсутствие калибровки и эксплуатационной проверки |

## Git и работа с изменениями

Полезно показать реальную историю репозитория и понять состояние рабочей копии:

```bash
git status
git log --oneline --max-count=8
git diff
git switch -c experiment/threshold-analysis
```

Рабочий процесс: отдельная ветка → небольшое связное изменение → проверки → commit с понятным сообщением → pull request с причиной изменения и результатами проверки. Объясните разницу между working tree, staging area и commit, а также между merge и rebase.

В этом проекте модель и локальное окружение исключены из Git; исходный код, пример входа, отчёт и test-предсказания сохранены. Коммерческий опыт и профессиональный грейд из этого репозитория не следуют.
